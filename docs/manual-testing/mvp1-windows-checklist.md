# MVP1 — ручная валидация на Windows

Выполняется на реальной Windows-машине с установленным официальным клиентом
Tiles Survive. Каждый пункт закрывает риск, который нельзя проверить
юнит-тестами на fake-реализациях (см. design doc, раздел 7).

1. `uv sync` на Windows ставит `pywin32` без ошибок.
2. `uv run python -m tiles_survive_automation.app` открывает GUI, в
   выпадающем списке окон виден запущенный клиент Tiles Survive.
3. Выбрать окно игры, нажать Record, выполнить в игре: обычный клик, клик
   правой кнопкой, drag (например, перетаскивание в инвентаре), прокрутку
   колёсиком, нажатие клавиши. Нажать Stop, сохранить как Rule с именем.
4. Проверить, что в `data/templates/<session_id>/` (уникальный подкаталог на
   каждую сессию записи, не на Rule) появились PNG для каждого клика, а в
   `data/screenshots/<session_id>/` — полные скриншоты окна на момент клика.
   Записать ВТОРОЙ Rule и убедиться, что его файлы попали в другой
   `<session_id>` и не перезаписали PNG первого Rule (это и есть инвариант,
   который важен: шаблоны разных записей никогда не коллизируют).
5. Нажать Play на сохранённом Rule — все действия должны воспроизвестись в
   тех же местах интерфейса игры (лог должен показывать `confidence` близко
   к 1.0 для visual-совпадений).
6. Свернуть окно игры перед Play — приложение должно активировать его через
   `SetForegroundWindow` перед выполнением первого шага.
7. Передвинуть окно игры на экране между Record и Play — relative-координаты
   и visual-поиск должны сработать одинаково (клиентские координаты, а не
   абсолютные экранные).
8. Во время Play нажать F9 — воспроизведение должно немедленно остановиться,
   зажатая (если была) кнопка мыши — отпуститься, даже если фокус в этот
   момент был в игре, а не в приложении.
9. Намеренно сломать один template (переименовать/удалить файл) и запустить
   Play — по дизайну приложения (fallback-цепочка Strategy 1 → 2 → 3) шаг со
   стратегией `VISUAL_THEN_RELATIVE` должен НЕ провалиться, а откатиться на
   relative-координаты (Strategy 2) и всё равно выполниться успешно — это и
   есть ожидаемое поведение, ради которого fallback существует. Чтобы
   проверить настоящий провал (Strategy 3 — когда ни одна стратегия не
   сработала), нужен шаг, у которого либо `strategy=RELATIVE_ONLY` без
   relative-параметров (уже покрыто юнит-тестом
   `test_stops_and_fails_when_no_strategy_resolves`), либо шаг, принудительно
   переведённый в `strategy=VISUAL_ONLY` со сломанным template — только в
   этом случае Play должен остановиться на шаге и записать ошибку в лог/БД.
10. Проверить многомониторную/масштабированную (125%/150% DPI) конфигурацию
    экрана — координаты клика не должны расходиться с реальным положением
    элементов интерфейса.

Отметить каждый пункт как пройденный/непройденный с комментарием перед тем,
как считать MVP1 завершённым.

## Повторная проверка (2026-08-18) — три находки с прошлого прогона

11. **Повтор п.4:** записать Rule и убедиться, что `data/templates/<session_id>/`
    и `data/screenshots/<session_id>/` реально появляются с PNG — раньше
    `cv2.imwrite` мог молча ничего не записать без видимой ошибки. Особенно
    важно перепроверить именно на пути с кириллицей (имя пользователя
    Windows/путь к репозиторию), если такой путь используется — это и был
    подозреваемый корень проблемы.
12. **Повтор п.7, но раздельно:** сначала передвинуть окно игры между Record и
    Play БЕЗ изменения размера — должно работать. Отдельно (другим прогоном)
    проверить только ресайз без перемещения — если сломается, это ожидаемое
    ограничение MVP1 (design-спека, раздел 7, риск №2), не баг. У тебя два
    монитора — если игра обычно живёт не на primary-мониторе, поведение
    курсора должно было исправиться (раньше код брал DPI не того монитора).
13. **Новое: ручной клик ЛКМ во время Play/Schedule должен прерывать
    выполнение** — так же, как F9 (отпускает зажатую кнопку, если была,
    останавливает Schedule даже во время паузы между батчами), и добавляет в
    лог строку `Manual click detected — run aborted`. Важно: клики, которые
    выполняет сам бот, НЕ должны сами себя прерывать — то есть обычный Play
    без вмешательства пользователя должен пройти от начала до конца, не
    спотыкаясь о собственные клики.
