# MVP2 / WaitForImage и WaitImageDisappear — дизайн-спецификация

Дата: 2026-08-21

Родительский документ: `docs/specs/2026-08-17-tiles-survive-automation-design.md`,
раздел 8, MVP 2. Опирается на уже реализованный Rule Editor
(`docs/specs/2026-08-18-...-wave1-design.md`,
`docs/specs/2026-08-19-...-wave2-design.md`).

## 1. Цель

Дать правилу возможность ждать не фиксированное время, а **визуальное
условие**: пока нужный элемент не появится на экране либо пока он не исчезнет.
Сейчас единственный способ пережить загрузку — записанный `Wait` на глазок:
поставишь мало — правило кликает по ещё не отрисованному интерфейсу, поставишь
много — прогон тянется вдвое дольше нужного.

Реализуются два типа шага, уже объявленных в `StepType`, но не исполняемых
движком: `WaitForImage` и `WaitImageDisappear`.

Родительская спека упоминает их «как verification и как самостоятельные
step-типы». Этот цикл делает **только самостоятельные шаги**. Verification
(условие, прикреплённое к другому шагу) и колонка `verification_json`
остаются неиспользованными до отдельного цикла — см. раздел 6.

## 2. Модель и хранение

Схема БД и миграции **не меняются**. Новые шаги используют поля, которые у
`RuleStep` уже есть:

| Поле | WaitForImage / WaitImageDisappear | Wait (добавленный вручную) |
|---|---|---|
| `params` | `{"timeout_ms": int, "poll_interval_ms": int}` | `{"duration_ms": int}` |
| `template_path` | путь относительно `templates_dir` | `None` |
| `confidence_threshold` | порог совпадения | не используется |
| `strategy` | всегда `VISUAL_ONLY` | всегда `VISUAL_ONLY` |

`strategy` для ожиданий смысла не имеет — relative-координат у них нет. Пишем
`VISUAL_ONLY`, потому что колонка `NOT NULL`, а в редакторе виджет гасим,
чтобы значение нельзя было испортить.

Значения по умолчанию для нового шага: `timeout_ms = 10000`,
`poll_interval_ms = 250`, `confidence_threshold` — из
`config.DEFAULT_CONFIDENCE_THRESHOLD`.

`RuleBuilder` не трогается: запись событий такие шаги не порождает и не должна.

## 3. Движок

### 3.1 Контракт `_execute_step`

Сейчас `_execute_step` сообщает о провале возвратом `None`, а `run()`
подставляет фиксированный текст `"step '<name>' could not be resolved by any
strategy"`. Для таймаута ожидания это сообщение ложное — провалилась не
стратегия разрешения точки, а условие на экране.

Возврат меняется на `StepFailure` — маленький dataclass в `playback/engine.py`
с единственным полем `message`. Три места в `_execute_step`, возвращавшие
`None` (`engine.py:114`, `:118`, `:136`), возвращают `StepFailure` с прежним
текстом, чтобы поведение и сообщения для обычных шагов не изменились. `run()`
проверяет `isinstance(outcome, StepFailure)` вместо `outcome is None`
(`engine.py:72`) и берёт текст оттуда. Внутренний контракт `_resolve_point`
не меняется — он по-прежнему возвращает `None`, когда точка не разрешилась,
и это разбирают его вызывающие.

Регрессия здесь закрыта существующим
`tests/unit/test_playback_engine.py::test_stops_and_fails_when_no_strategy_resolves`:
он должен продолжать проходить с прежним текстом сообщения.

### 3.2 Ожидание

Ветка добавляется в начало `_execute_step`, рядом с `WAIT` и `KEY_PRESS`, до
общего `grab` — у ожидания собственный цикл захвата:

```
deadline = monotonic() + timeout_ms / 1000
while monotonic() < deadline:
    frame = grab(client_rect)
    match = matcher.find(frame, template, confidence_threshold)
    condition = (match is not None) if WAIT_FOR_IMAGE else (match is None)
    if condition:
        return успех
    if abort_event.wait(poll_interval_ms / 1000):
        return успех  # прерывание разберёт проверка в начале цикла run()
return StepFailure(...)
```

При срабатывании abort ветка возвращает **успех**, а не провал: прерывание
разбирает проверка `self._abort_event.is_set()` в начале следующей итерации
цикла `run()`, которая ставит `STOPPED`. Так уже устроен обычный `Wait` —
ожидание не должно маскироваться под сбой шага, когда пользователь сам нажал
F9.

Пауза между опросами — через `self._abort_event.wait(...)`, а не `time.sleep`:
тот же приём, что у обычного `Wait`, чтобы **F9 прерывал ожидание немедленно**,
а не по истечении таймаута. Клиентский прямоугольник перечитывается один раз
перед циклом.

Успешный `WaitForImage` возвращает координаты центра совпадения и его
`confidence` — они попадают в `ExecutionStep`, как у обычного шага, и видны в
истории. У `WaitImageDisappear` совпадения в момент успеха нет, поэтому
координаты и confidence — `None`.

Описание для лога: `"WaitForImage matched after 1450ms (confidence=0.93)"` /
`"WaitImageDisappear satisfied after 800ms"`.

### 3.3 Провалы

- **Таймаут** — `StepFailure("step '<name>' timed out after <timeout_ms>ms
  waiting for the image to appear/disappear")`. По решению этого цикла таймаут
  **валит прогон**: `context.fail()`, `Execution.status = FAILED`,
  `ExecutionStep` с `result=FAILED` и этим текстом. Логика: если ожидаемый
  экран не появился, все последующие клики уйдут вслепую — ровно от этого
  фича и защищает. Для расписания это, по существующей логике
  `ScheduleController`, останавливает всё расписание.
- **Шаг без шаблона** (создали через Add step, но не сделали Recapture) —
  `StepFailure("step '<name>' has no template - use Recapture in the Rule
  Editor first")`. Проверяется до цикла, чтобы не уронить `cv2` и не крутить
  таймаут впустую.
- **Файл шаблона не читается** — `cv2.imread` вернул `None`:
  `StepFailure("step '<name>' template file is missing or unreadable:
  <path>")`. Отдельный случай, потому что на пути с не-ASCII символами
  `imread` молча отдаёт `None` (см. `recorder/image_io.py`).

## 4. UI: создание и правка

### 4.1 Add step

В `RuleEditorDialog` рядом с Up/Down/Delete появляется кнопка **Add step**.
Она открывает `ui/dialogs/add_step_dialog.py` — маленький `QDialog` с двумя
полями: тип (`WaitForImage` / `WaitImageDisappear` / `Wait`) и таймаут (для
`Wait` — длительность). Диалог ничего не сохраняет и не пишет на диск: он
возвращает готовый `RuleStep`, а вставку делает контроллер.

Шаг вставляется **после выделенного** (в конец, если ничего не выделено), и
сразу становится выделенным, чтобы следующий шаг пользователя — Recapture —
относился к нему.

`RuleEditorController.add_step(step, after_index)` — вставка плюс пересчёт
`order_index`, как это уже делают `move_up`/`delete_step`. Чистый Python,
тестируется без Qt.

### 4.2 Шаблон берётся существующим Recapture

Add step **не запрашивает картинку**. Новый шаг появляется в списке без
шаблона, и пользователь привязывает её уже существующей кнопкой **Recapture**
(клик по игре), а проверяет кнопкой **Test**. Это осознанное решение: весь
механизм захвата, маршалинга события с потока рекордера и обновления превью
написан и провалидирован в волне 2 — дублировать его внутри Add step незачем.

Следствие: между Add step и Recapture шаг существует в черновике в неполном
виде. Это допустимо — `save()` его сохранит, а движок при запуске выдаст
внятный отказ из раздела 3.3.

### 4.3 Панель полей

Добавляется спинбокс **Timeout (ms)** (диапазон 0..600000), пишущий в
`params`. Диалог собирает новый словарь и передаёт его через существующий
`update_step(index, params={...})` — метод контроллера менять не нужно.

Гашение виджетов по типу выбранного шага:

| Тип шага | name | enabled | delay | confidence | strategy | timeout |
|---|---|---|---|---|---|---|
| клики | + | + | + | + | + | — |
| WaitForImage / WaitImageDisappear | + | + | + | + | — | + |
| Wait | + | + | + | — | — | + |

Кнопка **Test** уже гаснет для шага без `template_path` — для ожиданий это
работает без изменений и остаётся осмысленным: Test показывает, видно ли
элемент прямо сейчас. **Run from here** для ожиданий тоже работает как есть.

## 5. Тестирование

Юнит-тесты движка на fake-реализациях (без Win32, без живой игры):

- `WaitForImage`: совпадение с первого кадра; совпадение на третьем опросе
  (fake-capture отдаёт разные кадры); таймаут — `FAILED` с текстом про
  timeout; `abort()` во время ожидания прерывает в пределах одного интервала
  опроса, а не по таймауту.
- `WaitImageDisappear`: зеркальные случаи — исчезло сразу, исчезло на третьем
  опросе, не исчезло за таймаут.
- Шаг без шаблона и шаг с нечитаемым файлом — свои сообщения.

Контроллер: `add_step` вставляет после указанного индекса, в конец при
`after_index=None`, пересчитывает `order_index`, не мутирует исходный список
при пустом черновике.

Диалог через `qtbot` + fake-реализации: Add step добавляет шаг выбранного типа
и делает его текущим; таймаут уходит в `params`; confidence и strategy гаснут
по таблице из 4.3; шаг ожидания без шаблона показывает `"No image"` в превью и
неактивный Test.

Ручной чек-лист `docs/manual-testing/mvp2-wait-for-image-checklist.md`
создаётся вместе с implementation plan и покрывает только то, что fake
принципиально не проверит: реальная загрузка экрана в игре, F9 во время
ожидания, поведение при таймауте на живом правиле.

## 6. Вне рамок

- **Verification** — ожидание, прикреплённое к другому шагу; колонка
  `verification_json` остаётся неиспользованной.
- **Добавление кликов через Add step** — только три типа из 4.1.
- **Настраиваемое поведение по таймауту** (`fail` / `continue` на выбор) —
  в этом цикле таймаут всегда валит прогон.
- Debug Mode и весь MVP3 — отдельные куски по родительской спеке.
